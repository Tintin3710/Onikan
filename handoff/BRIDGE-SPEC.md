# 한자 브리지 — 개발 스펙 (Kanji Bridge)

> **핵심 한 줄:** 학습 흐름을 바꾸지 말고, **뜻이 공개되는 순간(reveal)과 단어 상세에 "한국 한자음 연결"을 덧붙인다.** 한국인은 이미 아는 한자어를 지렛대로 일본어를 "이미 아는 것"으로 인식한다.
>
> 대상 앱: `taiyoungkim/AshitaKanji` (Expo · React Native) · 프로토타입: [`prototypes/bridge-spec.html`](./prototypes/bridge-spec.html)

## 0. 배경 (왜)
현재 학습 카드는 `한자+히라가나 → (탭) → 한국어 뜻 → 단어 상세` 순으로 **이미 80% 완성**. 그런데 `進度`의 뜻 "진도"는 *번역*이 아니라 **한국인이 이미 아는 그 단어(進度)**다. 지금은 이걸 밋밋한 뜻풀이로만 취급 → **"아 이거 아는 거였네"의 인식**으로 바꾸는 게 브리지다.

## 1. 범위 (무엇을)
흐름 순서는 **그대로 유지**. 아래 3가지만 추가한다.

### 1-1. reveal 카드에 "브리지 비트" (P0) — ⚠️ v3 소프트닝(인터뷰 반영)
> **인터뷰 발견(R3·R5):** "이미 아는 단어예요" 같은 **단정 어조는 '강요/억지'로 느껴진다.** → 유저를 단정하지 말고, **뜻 먼저 + 단어의 사실만** 서술.

`뜻 보기`를 눌렀을 때, **브리지 대상 단어**에 한해:
1. **뜻(한글) 먼저** — `진행 정도 · 명사`. (R3: "무슨 뜻인지 한국어 설명이 먼저 필요")
2. **소프트 연결 블록**(라벨 `한국어 연결`) — 단정 금지. 유저가 아니라 **단어의 사실**을 서술:
   - ✅ **`한국어 '진도(進度)'와 같은 한자`**  (fact)
   - ❌ ~~`너 이거 이미 알아` / `이미 아는 단어예요`~~ (assertion — 억지 유발)
   - 한자 병기(進度)로 동음이의(震度·珍島) 제거.
3. 발음 분해: **`しんど = シン〔진〕 · ド〔도〕`** (음독↔한국 한자음).
4. **예문은 그 아래 유지**(SRS 회상 위계 보존).

**문구 규칙:** 발견형/사실 서술만. 톤은 "짚어준다"가 아니라 "곁들여 알려준다". (R3·R5 재검증 대상)

### 1-2. 단어 상세 "한자 분해" — 옥편 표기 + 브리지 라인 (P0, 최저비용·최고효과)
한자 라벨은 **뜻만("나아가다") 쓰지 말고, 옥편/네이버 표준인 "훈뜻 + 한국음"**으로. 이게 업계 표준이자 **한국음을 자연히 노출**해 브리지에 유리하다.
```
進   나아갈 진                      ← 옥편 훈뜻+한국음 (뜻만 X)
     음독 シン  ≈  한국음 진         ← ★ 브리지 연결선 (핵심 차별점, 오렌지 강조)
     훈독 すす.む · すす.める
     부수 辵(쉬엄쉬엄갈 착) · 11획   ← 부수도 한글 풀이
```
**차별점:** 경쟁 앱(네이버·하루일본어 등)은 음독과 옥편음을 *나란히 보여주기만* 한다. 오니칸은 `음독 ≈ 한국음`을 **명시적으로 이어** "규칙적으로 대응함"을 각인시킨다 — 이게 브리지의 정체성.

### 1-3. 게이팅 (P0) — *오작동 방지 핵심*
브리지는 **음독 한자어(2자+ 복합어로 한국 한자어 대응이 뚜렷한 것)**에만 켠다.
- ✅ 켠다: `進度 しんど → 진도`, `図書館 としょかん → 도서관`
- ❌ 끈다(일반 흐름): 훈독·고유어(`山 やま`, `水 みず`), 화어/외래어, 한자 없는 히라가나 단어
- 잘못 켜서 억지로 "너 이미 알아"를 붙이면 신뢰가 깨진다 → **불확실하면 끈다.**

## 2. 데이터 요구사항
| 필요 데이터 | 출처 | 비고 |
|---|---|---|
| 한자별 **한국 한자음** | Unihan `kKorean` 필드 (KS X 1001) | KANJIDIC2와 코드포인트로 조인 |
| 한자별 **옥편 훈음**("나아갈 진") · 부수 한글풀이 | 한자 사전(훈음 데이터) | 라벨·부수 표기용 |
| 단어의 **음독 여부** | KANJIDIC2 / 사전 리딩 태그 | 리딩이 음독 조합인지 판정 |
| **한국 한자어 대응 + 뜻(sense)** | 한자음 조합 → 한국어 실단어 사전 대조 | 없으면 브리지 off · sense는 동음이의 제거용 |

**전처리(빌드타임 권장):** 단어 테이블에 `bridge`(단어) + 한자별 표기 필드를 미리 계산해 저장.
```jsonc
// word row 예시
{
  "jp": "進度", "reading": "しんど",
  "bridge": {                          // null 이면 게이팅 off
    "koWord": "진도",                  // 한국 한자어
    "koHanja": "進度",
    "sense": "진행 정도 · 명사",        // ★ 동음이의 제거용 뜻 gloss (필수)
    "map": [ { "on": "シン", "ko": "진" }, { "on": "ド", "ko": "도" } ]  // 음독↔한국음
  },
  "kanji": [
    { "c": "進", "oke": "나아갈 진", "jlpt": "N3",   // ★ 옥편 훈뜻+한국음 (뜻만 X)
      "on": "シン", "koOn": "진",                    // 브리지 라인: on ≈ koOn
      "kun": "すす.む · すす.める",
      "bushu": "辵(쉬엄쉬엄갈 착)", "strokes": 11 },
    { "c": "度", "oke": "법도 도 · 헤아릴 탁", "jlpt": "N3",
      "on": "ド·ト", "koOn": "도·탁",
      "kun": "たび · -た.い", "bushu": "广(집 엄)", "strokes": 9 }
  ]
}
```

## 3. 컴포넌트 상태
1. **Front** — 변경 없음 (`漢字` + 읽기 + 🔊 + "탭해서 뜻 확인")
2. **Reveal**
   - `bridge != null` → 인식 블록(1-1) + 기존 뜻/예문
   - `bridge == null` → 현행 그대로
3. **단어 상세** — 한자 분해 각 항목에 `한국음` 라인(1-2). `bridge` 유무와 무관하게, 데이터 있으면 표기.

## 4. 인수 조건 (Acceptance)
- [ ] `進度` reveal에서 **진도(進度) · 진행 정도**(한자+뜻 병기) + `しんど = シン〔진〕·ド〔도〕` 노출
- [ ] `ダンス`·`山(やま)` 등 훈독·외래어엔 브리지 블록이 **뜨지 않음**
- [ ] 단어 상세 한자 라벨이 **옥편 "나아갈 진"**(뜻만 X) + **음독 ≈ 한국음** 연결선 + 부수 한글풀이 표기
- [ ] `bridge` 계산이 빌드타임에 끝나 런타임 사전조회 없음
- [ ] 브리지 on/off가 리콜 흐름(뜻 보기 → 평가) 타이밍을 바꾸지 않음

## 5. 엣지 케이스
- **다중 음독**(度 = ド·ト·タク): 해당 단어에서 실제 쓰인 음독만 대응 표기.
- **훈독+음독 혼합어**(重箱/湯桶 읽기): 게이팅에서 제외(off)하거나 음독 형태소만 부분 표기 — v1은 **제외**.
- **한국음이 여러 개**(度 = 도·탁): 단어 문맥의 대응음 우선, 상세에선 `도·탁` 병기.
- **데이터 누락**: `bridge=null` + 한국음 미표기로 안전 폴백.

## 6. Non-goals (v1)
- 훈독어까지 억지 브리지 ❌
- 한자 어원/그림 설명 ❌ (별도 기능)
- 브리지 때문에 카드 순서/평가 UX 변경 ❌

## 7. 왜 이게 차별점인가 (컨텍스트)
듀오링고·WaniKani·Anki는 **영어 원어민 설계**라 한국 한자음 지렛대를 **구조적으로 못 쓴다.** 이건 한국어 네이티브 페다고지 = **복제 어려운 moat.** 효과가 큰 구간은 한자어 밀도 높은 **중급(N3~N1)** → 타겟(“기초 있는데 안 트이는 직장인”)과 일치. (근거·가설: `../PRD-v0.2.md`)
