# 기획·스펙 명세 작성 (Onikan)

기획/스펙/핸드오프 문서를 **일관된 포맷**으로 만들고, **누락 없이** 레포에 반영하기 위한 표준 절차다. 사용자가 매번 포맷을 지시하지 않아도 이 체크리스트로 문서를 완성한다.

## 언제 쓰나
- 화면·기능의 **동작/정책/상태**를 정리해야 할 때
- 기존 스펙을 **갱신·최신화**할 때 (리디자인 델타 포함)
- 개발자에게 넘길 **핸드오프 문서**를 쓸 때

## 산출 위치 & 정본 규칙
- 화면·기능 스펙 → `handoff/` 아래 (예: `handoff/redesign-YYYY-MM/README.md`, `handoff/<기능>-SPEC.md`)
- **토큰 정본 = `DESIGN.md`**, **컴포넌트 계약 = `COMPONENTS.md`**. 스펙은 이를 **참조**하고, 값이 충돌하면 **정본이 이긴다**(문서 안에 그 문장을 명시).
- 정본에 반영할 변경이 생기면 스펙 안에 **델타 표**로 남기고, 확정 시 정본에도 반영.

## 필수 섹션 (이 순서, 빠지면 안 됨)
1. **헤더** — 제목 / 상태(`Draft` \| `확정`) / **근거·출처**(Figma node·PNG·이전 결정 링크)
2. **핵심 변경 요약** — 갱신이면 무엇이 바뀌었는지 3~6줄
3. **조건 → 결과 표** — `| 조건 | 결과 |`
4. **동작 명세 표** — `| # | 상황 | 동작 |`
5. **상태·예외** — 상태 전이(가능하면 다이어그램) / 엣지케이스 / 빈·오류·로딩·비활성
6. **정책 결정 표** — `| ID | 사안 | 결정 |` · ID는 `O-1, O-2 …` **영구 고정**(재사용·재번호 금지)
7. **미확정 마커** — 확정 안 된 항목은 표 안에 `⚠️ 확인 필요 — …`로 표시. **확정되면** 표 제목을 "정책 결정(확정)"으로 바꾸고 마커 제거.
8. **변경 델타 표**(리디자인/버전업일 때) — `| ID | 항목 | 변경 |` (폐기 R-n / 신규 N-n / 규칙 D-n 등)
9. **관련 화면·컴포넌트 링크** — screens/PNG, 컴포넌트 이름, 관련 문서

## 완료 체크리스트 (커밋 전 반드시 확인)
- [ ] **조건표·동작표 둘 다** 있는가
- [ ] 상태·예외(전이/빈/오류/로딩) 포함
- [ ] **미해결 마커(⚠️) 개수 = 0** 인가? (남아 있으면 문서 상단에 "남은 것 O-x" 목록으로 명시)
- [ ] 정책마다 **ID(O-n)** 부여, 기존 ID 그대로 유지
- [ ] **DESIGN.md·COMPONENTS.md와 충돌 없음**(있으면 정본 우선 + 델타 표에 기록)
- [ ] 근거/출처 링크, 관련 화면/컴포넌트 링크
- [ ] 갱신이면 **변경 델타 표** + 정본 반영 여부 표기

## Do / Don't
- **Do** — 정책은 결정문("~로 확정")으로, 조건·동작은 **표**로, 애매하면 숨기지 말고 `⚠️`로 남긴다.
- **Don't** — 산문으로만 서술 / 미확정을 조용히 누락 / ID 임의 변경 / 정본과 다른 값 방치.

## 갱신 절차 (요약)
1. 대상 문서 읽기 → 2. 바뀐 조건·동작·정책 반영 → 3. `⚠️` 마커 갱신(해결분 제거) → 4. 델타 표 작성 → 5. `DESIGN.md`·`COMPONENTS.md` 정합 확인 → 6. 커밋 `spec: <요약>`.

## 시작 방법
`TEMPLATE.md`를 복사해 채운다. (같은 폴더의 템플릿)
